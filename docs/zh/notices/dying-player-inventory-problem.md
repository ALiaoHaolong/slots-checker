# 死亡玩家背包问题

廖浩龙 2026.11.18

## 影响版本

本模组支持的所有版本（1.18 至 26.3）。  
原版问题截至 2025-10-23（MC-248983 最后一次更新）仍未修复。

## 分析

### 原版问题

当玩家在未开启 `keepInventory` 游戏规则的情况下死亡时，`PlayerInventory.dropAll()` 会在死亡瞬间清空所有槽位，并将物品作为物品实体掉落至地面。随后该玩家实体被丢弃并替换：`PlayerManager.respawnPlayer()` 会构建一个新的 `ServerPlayerEntity`，再调用 `copyFrom()` 从旧实体搬运状态。

`copyFrom()` 仅在三种情况下克隆背包：玩家仍然存活（比如从末地中央的传送门返回主世界）、`keepInventory` 已开启、或旧玩家是旁观者。其余情况下，游戏将跳过克隆背包的步骤（推测的理由是背包理应在死亡时已被清空，从而不需要克隆背包）。

因此，在死亡期间写入背包的任何内容都会被直接丢弃。这就是 MC-248983。

### 本模组为何需要处理这个问题

原版没有任何方式能将容器 GUI 指向另一位玩家的背包，因此在未安装模组的游戏中，唯一的写入者是命令，而几乎没有人会把命令对准一个正停在死亡界面上的玩家。本模组的功能恰恰就是这件事，并且它通过一个普通的 GUI 接受写入。于是触发该问题最自然的方式变成了：以编辑模式打开目标的背包，目标死亡，`keepInventory` 未开启，在窗口期内放入一件物品，然后看着它在重生后消失。

### 末影箱为何不受影响

`copyFrom()` 以引用方式转移末影箱，且是无条件的。因此末影箱的内容在重生后完整保留，窗口期内的写入也会生效。

## 处理

处理必要性：

- 相较于原版，本模组触发该问题的概率大大提升，因为它把一个命令行的边缘情况变成了一次 GUI 操作。
- 与创造模式背包问题不同，这里的后果是物品丢失而非物品复制，严重程度远高于前者。
- 这是服务端行为，本模组能够缓解；而不像创造模式背包问题是客户端问题，仅服务端模组无从修复。

处理方案：窗口期内暂停交互，并保持界面打开。

本模组不改变原版对物品的处理方式，只是拒绝一次会被原版静默销毁的写入。具体而言，在编辑模式下、针对非末影箱槽位、当目标死亡且 `keepInventory` 未开启时：

- 目标槽位被渲染为屏障物品，这是所有玩家都已熟知的"该槽位不可用"信号。
- `canInsert` 与 `canTakeItems` 返回 false，因此左键、Shift 左键、数字键交换、拖拽以及丢弃键都无法将任何物品移入或移出。

当目标重生后，模组通过 `AFTER_RESPAWN` 监听将 GUI 重新绑定到新的玩家实体，并自动恢复编辑功能。管理员只需等待并观察，无需重新执行命令。

末影箱槽位豁免于上述全部内容，理由见分析一节。
